# 239 Release preflight fails every fresh fork with 'npm OIDC package exchange rejected (404); configure a trusted publisher or bootstrap token' without saying which action applies

## Summary

In every new repository created from this template, the first push to `main` fails the release preflight with a message that doesn't say what to do:

```
FAIL: npm OIDC package exchange rejected (404); configure a trusted publisher or bootstrap token
##[error]release-preflight: npm OIDC package exchange rejected (404); configure a trusted publisher or bootstrap token
```

(konard/voice-simulator `main`, run 39021393361, job "Release Preflight".)

npm's OIDC exchange answers 404 in two different situations, and each needs a different maintainer action:

1. **The package has never been published.** npm can attach a trusted publisher only to an existing package, so "configure a trusted publisher" cannot be done yet. The only fix is an `NPM_TOKEN` repository secret for the first release. After that, add the trusted publisher and delete the secret.
2. **The package exists but has no trusted publisher for this repository and workflow.** The fix is the package's trusted publisher settings.

The current message names neither the secret's settings URL, nor the npm access page, nor which case applies. For a repository fresh from the template it is always case 1, and "configure a trusted publisher" sends the maintainer to a page that can't help.

## Suggested fix (applied and verified in konard/voice-simulator#4, commit d64bf2d)

On a 404 without `NPM_TOKEN`, look up the public package document (`GET $NPM_REGISTRY/<package>`) and report the matching action:

```sh
# The exchange answers 404 both for an unpublished package and for a package
# without a trusted publisher. The public package document tells them apart,
# so the failure names the maintainer action that fixes this repository.
explain_npm_exchange_404() {
  local package="$1" name repo secrets access status
  name=$(node -e 'process.stdout.write(decodeURIComponent(process.argv[1]))' "$package" 2>/dev/null)
  repo="${GITHUB_REPOSITORY:-this repository}"
  secrets="${GITHUB_SERVER_URL:-https://github.com}/${GITHUB_REPOSITORY:-OWNER/REPO}/settings/secrets/actions"
  access="https://www.npmjs.com/package/${name}/access"
  status=$(http "$NPM_REGISTRY/$package")
  status="${status##*"$NEWLINE"}"
  case "$status" in
    404)
      bad "npm has no package ${name} yet, and npm configures trusted publishing only for published packages. Add an NPM_TOKEN repository secret (a granular token allowed to publish ${name}) at ${secrets} for the first release, then add a trusted publisher for ${repo}, workflow release.yml, at ${access} and delete the secret"
      ;;
    200)
      bad "npm rejected the OIDC exchange for ${name} (404): add a trusted publisher for ${repo}, workflow release.yml, at ${access}"
      ;;
    *)
      bad "npm rejected the OIDC exchange for ${name} (404) and the package lookup answered ${status:-no status}: add a trusted publisher at ${access}, or an NPM_TOKEN repository secret at ${secrets} if the package was never published"
      ;;
  esac
}
```

and call it in place of the generic `bad` in the `404)` branch of `check_npm_oidc`. Tests in `tests/release-preflight.test.js` use the existing curl stub (`tests/fixtures/preflight-stub/curl`, extended to answer the package lookup) and cover all three branches.

The `SKIP: NPM_TOKEN is not set ... (NPM_TOKEN is the documented bootstrap fallback, issue #77)` line also cites an issue number from another repository's history. It could say what the fallback is for: "NPM_TOKEN is the bootstrap fallback for a package npm does not have yet".

References:
- npm trusted publishing: https://docs.npmjs.com/trusted-publishers
- `npm trust` prerequisites list "the package must already exist on the npm registry": https://unpkg.com/npm@11.11.1/docs/content/commands/npm-trust.md
